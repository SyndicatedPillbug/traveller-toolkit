## Overview

Traveller Toolkit is an Obsidian plugin (v0.3.0) for Traveller TTRPG referees. It provides system-first Traveller tools including UWP generation, subsector management, Traveller Map compatibility, and Dossier Engine v4 non-AI prose generation.

The plugin is undergoing a **major rebuild** from a single-file TypeScript project (1163 lines in main.ts) to a **modular architecture** with proper separation of concerns. The rebuild uses the Obsidian sample plugin structure with a modular `src/` directory.

**Current branch**: `rebuild/modular`

**Target**: Modular, testable, maintainable codebase

### File Discovery (src/vault/FileDiscoveryService.ts)

The `findSystemByHex()` method implements **metadata-first search**:
1. **Primary**: Match frontmatter `hex` or `system_hex` field with `type: system`
2. **Fallback**: Folder name matches pattern `{hex} - {name}` with file starting with `_`
3. **Legacy**: `_System.md` in folder named `{hex} - {name}`

This is **critical for the promote bug fix** - it allows finding systems even when they've been moved from `Systems/` to `Traveller/Systems/`.

## Coding Conventions

### TypeScript

- **Target**: ES2018
- **Module**: ESNext
- **Strict null checks**: Enabled
- **Module resolution**: Node10
- **No implicit any**: Disabled in config, but prefer explicit types

### Code Style

- **Naming**:
  - Variables/functions: camelCase
  - Classes/types: PascalCase
  - Constants: UPPER_SNAKE_CASE
  - Private members: Prefix with `_` (not enforced)
- **Indentation**: 2 spaces
- **Braces**: Opening on same line, closing on new line
- **Semicolons**: Required
- **CSS prefix**: `.ttk-` for all plugin styles

### Module Structure

Each module follows this pattern:
```
src/module/
├── types.ts       # Module-specific interfaces
├── constants.ts   # Module constants
├── service.ts     # Main service/class
└── index.ts       # Optional exports
```

### Service Pattern

Vault services follow the **service pattern**:
1. Single responsibility per service
2. Dependencies passed via constructor
3. App reference stored but not exposed in public API
4. Pure methods where possible (no side effects on app)

Example:
```typescript
export class VaultService {
  constructor(private app: any) {}
  
  getFile(path: string): TFile | null {
    // Uses this.app.vault internally
  }
}
```

### Tool Pattern

Tools follow the **tool pattern**:
1. Implement `TravellerTool` interface (id, label, render, onUnload?)
2. Receive plugin and services via constructor
3. Render into provided container
4. Cleanup in onUnload if needed

### Frontmatter Handling

**Always use FrontmatterService**, never parse YAML manually (except in fallback):
```typescript
// Good
const fm = this.services.frontmatter.getFrontmatter(file);
await this.services.frontmatter.processFrontmatter(file, fm => { ... });

// Bad - manual parsing
const content = await this.app.vault.read(file);
const match = content.match(/---\n([\s\S]*?)\n---/);
```

### Path Handling

**Always use VaultService methods**, never assume path structure:
```typescript
// Good
const file = this.services.vault.getFile(path);
const exists = await this.services.vault.fileExists(path);

// Bad - direct vault access
const af = this.app.vault.getAbstractFileByPath(path);
if (af instanceof TFile) { ... }
```

### Wikilink Conversion

**Always use LinkService**, never string manipulation:
```typescript
// Good
const wikilink = this.services.link.pathToWikilink(path, label);
const path = this.services.link.wikilinkToPath(wikilink);

// Bad - manual string manipulation
const wikilink = `[[${path}|${label}]]`;
```

## Anti-Patterns and Forbidden Changes

### Never Do These

1. **Don't modify generated files**: `main.js`, `main.js.map`
2. **Don't modify node_modules/**: Use npm for dependencies
3. **Don't change plugin ID**: `traveller-toolkit` is hardcoded in manifest.json
4. **Don't remove type safety**: Keep TypeScript compiler options strict
5. **Don't hardcode paths**: Use VaultService and normalizePath()
6. **Don't trust frontmatter paths blindly**: Real TFile.path wins over frontmatter
7. **Don't silently fail**: Use `new Notice()` for user errors, `console.log` for debugging

### Avoid These

1. **Don't use direct app.vault access**: Use VaultService methods
2. **Don't manually parse frontmatter**: Use FrontmatterService
3. **Don't manually convert wikilinks**: Use LinkService
4. **Don't assume settings folder**: Use loadedSystem.systemFolder when available
5. **Don't create files without checking**: Use SafeWriteService.createFileIfMissing
6. **Don't overwrite existing notes**: Check before creating
7. **Don't use async without await**: Obsidian API is async
8. **Don't assume plugin reference exists**: Check this.plugin before accessing

### Code Quality

1. **Follow LoadedSystem as source of truth**: Once a system is loaded, use its systemFile and systemFolder
2. **Use FileDiscoveryService**: Don't re-implement system finding logic
3. **Use SafeWriteService**: Don't directly call vault.create/vault.modify
4. **Type all service dependencies**: Services should have proper types, not `any`
5. **Add debug logging**: Use `console.log` with prefix `[Traveller Toolkit]` for debugging

## Promote Bug Fix Context

**The Problem**: Promotion fails when systems have been moved from `Systems/` to `Traveller/Systems/` because the code uses `this.settings.systemsFolder` instead of the actual loaded system's folder.

**The Solution** (already implemented in FileDiscoveryService):
1. LoadedSystem stores the actual `systemFile` (TFile) and `systemFolder` (string)
2. FileDiscoveryService.findSystemByHex() uses metadata-first search (frontmatter hex match)
3. FileDiscoveryService.findSystemFromActiveFile() resolves system from any related note
4. Promote should use `loadedSystem.systemFolder`, not `settings.systemsFolder`

- `src/app/types.ts` - LoadedSystem interface (COMPLETE)
- `src/tools/system-generator/SystemGeneratorTool.ts` - **NEEDS IMPLEMENTATION**
